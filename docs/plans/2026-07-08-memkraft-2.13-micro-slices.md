# MemKraft 2.13 «Capture & Resolve» — TDD Micro-Slices

**날짜:** 2026-07-08
**전제:** [refined roadmap](2026-07-08-memkraft-v3-fable5-refined-roadmap.md) §3.1(2.13 범위), §9(10개 태스크), §10.9(micro-slice 방침)
**대상 독자:** 2.13을 구현하는 에이전트/개발자. 각 슬라이스는 **한 세션 안에 red → green → refactor가 끝나는 크기**로 절단되어 있다.

**공통 규칙:**

- 모든 슬라이스는 **테스트 먼저**(red) 쓴다. 테스트가 실패하는 것을 확인한 뒤 구현한다.
- 각 슬라이스는 단독 커밋/머지 가능해야 하고, 머지 시점에 기존 테스트 + `search_recall` 게이트가 그린이어야 한다.
- 슬라이스 안에서 "하는 김에" 다음 슬라이스 범위를 건드리지 않는다. 발견한 문제는 코드가 아니라 이 문서의 해당 슬라이스에 메모로 남긴다.
- 새 공개 API는 전부 `preview` 티어로 문서화한다(roadmap §10.2).
- Python 코드 스타일·모듈 배치는 기존 `src/memkraft/` 관례를 따른다.

**슬라이스 의존성:**

```text
S1 → S2 → S3 → S4          (store_core 축)
S5 → S6 → S7               (gym/CI 축, S1과 병렬 가능)
S8 → S9                    (extract_claims 축, S1과 병렬 가능)
S1 → S10 → S11             (candidate → overlay)
S8,S10 → S12               (resolver는 claims와 candidate 이후)
S1 → S13                   (last interaction)
```

임계 경로는 S1→S10→S12 (store_core → candidates → resolver). S5~S9, S13은 병렬 진행 가능.

## S1. store_core: append/read only (tombstone 없음)

**목표:** `src/memkraft/store_core.py` 신설. envelope v1 레코드의 원자적 append와 순차 read만.

**Red (테스트 먼저):** `tests/test_store_core.py`

1. `append(path, record)` 후 `read_all(path)`이 그 레코드를 반환한다.
2. append된 레코드에 `id`, `schema_version == 1`, `created_at`(UTC ISO-8601)이 자동 채워진다. 호출자가 넘긴 payload 필드는 보존된다.
3. 파일이 없으면 append가 생성한다(부모 `.memkraft/` 포함).
4. corrupt line(잘린 JSON)이 섞인 파일에서 `read_all`은 해당 라인을 스킵하고 나머지를 반환하며, 스킵 건수를 보고한다.
5. append는 개행으로 끝나는 단일 라인을 쓴다 (파일을 바이트로 읽어 검증).

**Green 범위:** envelope 생성, `fcntl.flock` 배타 락 + 단일 `write()` 호출, JSONL reader. **tombstone·컴팩션·스냅샷은 이 슬라이스에서 구현 금지.**

**Done:** 위 5개 테스트 그린. 공개 함수는 `append`/`read_all`(이름은 구현 시 확정하되 internal 티어) 2개뿐.

## S2. store_core: tombstone filtering only

**목표:** tombstone reader 계약 — 모든 read 경로가 tombstone 레코드를 기본 은닉한다. (THREAT_MODEL T5의 2.13 몫)

**Red:**

1. `tombstone: true` 레코드는 `read_all` 기본 호출에서 미노출.
2. `read_all(include_tombstoned=True)`는 노출 (컴팩션·감사용 내부 경로).
3. `mark_tombstone(path, record_id)`는 원본을 수정하지 않고 tombstone 마커 레코드를 append한다 (append-only 불변식). 이후 read에서 해당 `id` 미노출.
4. 존재하지 않는 `id`에 대한 `mark_tombstone`은 구조화 에러.

**Green 범위:** 마커 append + read 시 id 단위 suppression. 물리 삭제는 S3(컴팩션)의 일.

**Done:** 4개 테스트 그린 + S1 테스트 무회귀.

## S3. store_core: compaction only

**목표:** tombstone된 레코드와 마커의 물리 제거.

**Red:**

1. `compact(path)` 후 tombstone된 레코드·마커가 파일에서 물리적으로 사라지고, live 레코드는 순서 보존.
2. compact는 temp 파일 재작성 + `os.replace` (compact 도중 kill해도 원본 또는 완성본만 존재 — temp 파일 잔존 시 재실행이 정리).
3. corrupt line은 compact 시 제거되고 제거 건수가 반환된다.
4. 빈 파일/파일 없음에 대한 compact는 no-op 성공.

**Green 범위:** 재작성 + `os.replace` + 락. 자동 compact 트리거(크기/주기)는 **비범위** — 2.13에서는 명시 호출만.

**Done:** 4개 테스트 그린. crash-safety는 temp 파일을 남긴 상태를 시뮬레이트해 검증.

## S4. store_core: concurrency test only

**목표:** 코드 추가 없이(필요 시 락 버그 수정만) 동시성 게이트를 테스트로 고정.

**Red:** `multiprocessing`으로 **4 프로세스 × 250 append** 후:

1. 총 1000 레코드, corrupt line 0건, `id` 중복 0건.
2. 동시 append 중 `read_all` 반복 호출이 예외 없이 동작(부분 라인 미노출).
3. append 경쟁 중 `compact` 1회 삽입 시에도 live 레코드 유실 0건.

**Done:** 3개 테스트 그린, CI에서 안정적(타이밍 의존 flake 없게 재시도 없이 3연속 통과 확인). 이것이 roadmap §3.1 동시성 게이트의 구현체다.

## S5. Gym registry: 신규 시나리오명 수용 + stub metrics

**목표:** `benchmarks/gym/run.py`의 `--scenario` choices 하드코딩(`["search_recall"]`)을 레지스트리로 교체.

**Red:**

1. 레지스트리에 시나리오를 등록하면 `--scenario <name>`으로 실행 가능.
2. 미등록 시나리오명은 구조화 에러 + 비제로 종료 (traceback 아님).
3. stub 시나리오(고정 metrics 반환)를 등록해 end-to-end로 JSON 출력 스키마(`{scenario, thresholds, observed, pass, baseline_ref}`) 검증.
4. 기존 `search_recall` 동작·출력 무변화 (기존 호출 시그니처 유지).

**Green 범위:** 레지스트리 dict + 등록 함수. 실제 신규 시나리오 구현은 각 기능 슬라이스(S11, S12, S13)의 일.

**Done:** 4개 테스트 그린. `benchmarks/gym/scenarios.py`에 등록 지점 주석 1줄.

## S6. Gym: 구조화 threshold 실패

**목표:** 게이트 실패와 파라미터 오류가 traceback이 아닌 구조화 JSON + 비제로 종료로 끝난다.

**Red:**

1. 임계값 미달 시 stdout에 `{scenario, thresholds, observed, pass: false, baseline_ref}` JSON, 종료 코드 1.
2. 잘못된 파라미터(음수 top_k, 비유한 gate 값 등)는 `{error: {kind, message, param}}` 구조화 JSON, 종료 코드 2, traceback 미출력.
3. 임계값은 `benchmarks/gym/gates.py`의 명명 상수에서만 온다 — 시나리오 코드에 매직 넘버로 임계값을 두면 실패하는 테스트(상수 참조 검증).

**Done:** 3개 테스트 그린. 종료 코드 규약(0 pass / 1 gate fail / 2 usage error)을 `benchmarks/gym/run.py` docstring에 명문화.

## S7. CI: search_recall만 먼저

**목표:** `.github/workflows/gym-gate.yml` 신설 — `src/` 또는 `benchmarks/` 변경 PR에 `search_recall` 게이트 강제.

**Red(검증 방식):** workflow는 pytest 대상이 아니므로, (a) 로컬에서 `PYTHONPATH=src python3 benchmarks/gym/run.py --scenario search_recall --gate` 그린 확인, (b) PR로 올려 CI 실행 자체를 확인, (c) 게이트를 일부러 깨는 커밋으로 red 확인 후 revert.

**Green 범위:** pytest 전체 + `search_recall --gate` 두 스텝. Python 3.9와 3.12 매트릭스(pyproject의 지원 하한/상한 근사). **신규 시나리오 추가는 이후 각 슬라이스가 workflow에 한 줄씩 추가** — 이 슬라이스에서 미리 등록하지 않는다.

**Done:** PR에서 그린/레드 양쪽 확인 완료. 브랜치 보호 규칙에 required check 등록.

## S8. extract_claims: 영어 4패턴만

**목표:** `extract_claims(text, *, entity_hint=None) -> list[dict]` — 규칙 기반, stdlib만, 영어 4패턴.

지원 패턴(roadmap §10.7 — 이 목록 밖은 전부 미추출):

1. `X prefers Y`
2. `X uses Y`
3. `X is located at/in Y`
4. `X changed/updated/corrected Y to Z`

**Red:** 라벨 fixture (`tests/fixtures/claims_en.json`, 패턴당 긍정 ≥ 5 + 부정 ≥ 5):

1. 각 패턴에서 `{subject, predicate, object_value, source_quote, confidence}` 정확 추출, `source_quote`는 입력의 실제 substring.
2. 패턴 4에서 `valid_from`은 텍스트에 명시 날짜가 있을 때만 채워진다.
3. 부정 fixture(패턴 유사 비클레임 문장)에서 추출 0건 — **false positive 최소화가 recall보다 우선.**
4. 추출 실패 시 빈 리스트(예외 아님).
5. 결정성: 동일 입력 100회 호출 동일 출력.

**Green 범위:** 정규식/토큰 규칙. NLP 라이브러리·LLM·휴리스틱 확장 금지.

**Done:** fixture 전부 그린. false positive 0건이 게이트다.

## S9. extract_claims: 한국어 4패턴만

**목표:** S8과 동일 계약으로 한국어 최소 패턴 추가.

지원 패턴:

1. `X는 Y를 선호`
2. `X는 Y를 사용`
3. `X는 Y에 있음`
4. `X를 Y로 수정/변경`

**Red:** `tests/fixtures/claims_ko.json` (패턴당 긍정 ≥ 5 + 부정 ≥ 5):

1. 조사 변형(은/는, 을/를) 허용 범위를 fixture로 고정 — fixture에 없는 변형은 지원 안 함이 정답.
2. NFC 정규화 후 매칭 (자소 분리 입력 fixture 1건 포함).
3. 한/영 혼합 문장에서 영어 패턴과 충돌 없음 (S8 fixture 재실행 무회귀).
4. 부정 fixture 추출 0건.

**Green 범위:** S8 구조에 패턴 테이블 추가만. 형태소 분석기 도입 금지.

**Done:** ko fixture 그린 + en fixture 무회귀.

## S10. remember_candidate: envelope 쓰기만 (resolver 미연동)

**목표:** `remember_candidate` / `list_candidates` — `candidates.jsonl`에 envelope v1으로 쓰고 읽는 것까지만.

**Red:**

1. `remember_candidate(text, session_id=..., entity_hint=None)`가 `candidates.jsonl`에 envelope 레코드를 append하고 `candidate_id`를 반환한다.
2. 레코드에 `expires_at`(기본 TTL 24h)과 `provenance_id`(없으면 명시적 `"unknown"`)가 채워진다 — `provenance_coverage` 게이트 100%의 구현체.
3. `list_candidates(session_id=...)`는 만료 후보를 기본 제외하고, `include_expired=True`로 노출.
4. tombstone된 후보는 `list_candidates`에 미노출 (S2 계약 준수 — reader가 store_core를 통해서만 읽는지 검증).
5. `claims` 필드는 **이 슬라이스에서는 항상 빈 리스트** — extract_claims 연동은 S12 직전 접합 커밋에서.

**Green 범위:** store_core 위의 얇은 도메인 계층. 검색/오버레이 미포함.

**Done:** 5개 테스트 그린.

## S11. session overlay

**목표:** `session_overlay(session_id, query, top_k)` — 세션 스코프 후보에 대한 토큰 중첩 검색, `memory_state: "session_overlay"` 라벨 스키마 강제.

**Red:** fixture 20건 (roadmap 게이트 그대로):

1. 동일 세션 즉시 재현 1.00 — 방금 `remember_candidate`한 텍스트가 같은 세션 `session_overlay`에서 검색된다.
2. **타 세션 누출 0건** — 세션 B의 쿼리에 세션 A 후보 미노출 (THREAT_MODEL T4).
3. 만료 후보 노출 0건.
4. 모든 결과 아이템에 `memory_state == "session_overlay"` — 반환 직전 스키마 검증 함수가 강제하고, 라벨 누락 시 예외.
5. 결과가 기존 `search` 결과와 절대 혼합되지 않는다 (별도 API, 별도 반환형).

**Green 범위:** 토큰 중첩 스코어링(stdlib). 임베딩·BM25 미사용.

**Done:** 5개 테스트 그린 + `session_overlay_recall` Gym 시나리오를 S5 레지스트리에 등록, 게이트 임계값(재현 1.00 / 누출 0 / 만료 노출 0)을 `gates.py` 상수로.

## S12. resolver dry-run

**목표:** `resolver_dry_run(claims: list[dict]) -> list[verdict]` — 8개 verdict, 결정적 규칙만.

**선행 접합 커밋:** `remember_candidate`가 `extract_claims`를 호출해 `claims` 필드를 채우도록 연결 (S8+S10 산출물의 접합 — C2 단절 해소 지점). 접합 자체의 테스트: 후보 저장 시 4패턴 텍스트에서 claims가 채워지고, 그 외 텍스트는 빈 claims + `CANDIDATE_REVIEW` 표시.

**Red:** 라벨 fixture 120케이스 (`tests/fixtures/resolver_cases.json` — 8 verdict × 15케이스, 지시문형 악성 클레임 포함):

1. verdict 정확도 ≥ 0.95 (`gates.py` 상수).
2. 결정성 1.00 — 동일 입력 100회 동일 출력.
3. **`source_quote` 부재 클레임의 active 승격 경로 0건** — verdict가 무엇이든 승격 불가 (THREAT_MODEL T2).
4. dry-run은 어떤 스토어에도 쓰지 않는다 (파일시스템 해시 전후 동일).
5. 잘못된 claims dict(필수 키 누락)는 구조화 에러.

**Green 범위:** 결정적 규칙 테이블. LLM·임베딩 금지. verdict 8종의 이름과 의미는 구현 PR에서 fixture와 함께 확정하고 docstring에 명문화.

**Done:** 5개 테스트 그린 + `resolver_verdicts` Gym 시나리오 등록.

## S13. last-interaction index

**목표:** `record_interaction` / `last_interaction` — append 로그 + 주기 스냅샷 구조.

**Red:**

1. `record_interaction(subject_id, occurred_at, interaction_id, ...)` append 후 `last_interaction(subject_id)`이 최신 상호작용 반환.
2. **역순 삽입 포함 200 이벤트에서 정확도 1.00** — `occurred_at` 단조 갱신(과거 이벤트가 나중에 도착해도 최신값 유지).
3. `occurred_at` 동률 시 `interaction_id` 사전순 tie-break (fixture로 고정).
4. 스냅샷(`last_interactions.json`)이 없거나 깨져도 로그에서 전체 재구성 — 파생 뷰 원칙.
5. p95 < 5ms @ 10k subjects (웜 200회 측정, `gates.py` 상수).

**Green 범위:** `last_interactions.jsonl`(envelope, store_core 사용) + 스냅샷 재작성(temp + `os.replace`). 스냅샷 주기는 단순 규칙(N append마다)으로 시작.

**Done:** 5개 테스트 그린 + `last_interaction` Gym 시나리오 등록.
