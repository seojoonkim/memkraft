# v2.8.1 baseline analysis + v2.8.2 roadmap

*Run date: 2026-05-14, Mac mini M-series (Asia/Seoul)*

This doc captures (a) the **post-v2.8.1 baseline** on the standard
`benchmarks/search_cache_bench.py` workload, (b) a fresh corpus
**scaling probe** at 10 / 50 / 100 / 500 / 1000 entities, (c) **cProfile
hot-path** analysis on v2.8.1, and (d) the two **v2.8.2 perf changes**
that landed in `perf/v282-touch-throttle`.

## 3. v2.8.1 hot-path profile

`cProfile`, 200 entities, 100 cold queries:

```
cumtime  ncalls  function
1.369s   100     core.py:1056 search        ← whole search loop
0.215s   40200   _core_lifecycle_helpers.py:77 all_md_files
0.191s   3000    core.py:3446 _touch_last_accessed  ← write-on-read!
0.154s   20000   core.py:3436 _safe_read
0.124s   20000   _read_cache.py:50 get_or_read
0.118s   20000   strptime (recency bonus, per doc per query)
0.109s   20000   pathlib.py relative_to
0.098s   20000   core.py:3491 _best_token_snippet  (already tuned in 2.8.1)
0.077s   40000   posix.lstat (is_symlink during file walk)
```

Two findings stuck out:

### Finding A — `_touch_last_accessed` writes a *body* field, not the
`last_accessed:` frontmatter that `decay.py` actually reads.

Search hits update the markdown body string `**Last Accessed:** …`,
but the decay scorer (`decay.py:_read_decay_fm` → `last_accessed`
YAML key) is fed entirely by `decay_apply` / `tier_touch` / explicit
`decay_promote`. The body-field write is purely cosmetic and was
costing 13 % of the search cumtime by issuing up to 20 disk writes
per query for the top-K result paths.

### Finding B — `strptime("%Y-%m-%d")` is being called per-doc, per
query, for the recency-bonus heuristic.

The latest bracketed date in a markdown body almost never changes
between queries, and even across the whole corpus there are only a
few hundred distinct date strings. 20000 calls × ~6 µs each is dead
work that a one-line cache eliminates.

## 4. v2.8.2 changes (this branch)

### Change 1 — touch-throttle (`_core_lifecycle_helpers.touch_last_accessed`)

* Per-process LRU-bounded dict of `path → last_touch_unix`.
* Skip the read-modify-write if same path was touched within
  `MEMKRAFT_TOUCH_THROTTLE_SECONDS` (default **60 s**).
* `MEMKRAFT_DISABLE_TOUCH_LAST_ACCESSED=1` disables it entirely (handy
  for read-only audits or perf-sensitive batch jobs).
* Also short-circuits the `write_text` when the rewritten content would
  be byte-identical (the legacy path always wrote, even when no
  `Last Update` / `Tracking Config` anchor was found).
* Bounded at 4096 entries — oldest entry evicted past the cap so the
  map can't grow unbounded on a million-doc corpus.

### Change 2 — `_iso_date_to_datetime` memoisation (`core.py`)

* Module-level dict keyed by the literal date string.
* Hard ceiling at 4096 entries (cache clears on overflow).
* Returns `None` on parse failure so callers branch instead of
  catching `ValueError` per row.
* Applied at both search-loop recency-bonus sites (line 1226 and
  ~line 2300 in `recall`-rerank). The remaining `strptime` calls in
  `core.py` (line 2000 `dream-cycle` summariser, line 3785 calendar
  date pinning) are cold paths and were left alone.

## 5. P3 (inverted posting list) — evaluation memo

**Goal**: turn the current O(N · token-set) scoring loop into
O(matched-docs · token-set) by maintaining `token → doc_freq + list[(doc, tf)]`
maps, so single-token rare queries can skip the long tail entirely.

### Where it would plug in

* `_corpus_index.CorpusIndex` already stores `token_doc_freq` and a
  per-doc `doc_token_freqs[doc]`. The natural extension is an
  **inverted form**: `postings[token] = list[(doc, tf)]`, built once
  per corpus generation alongside the forward index.
* `core.py:search` (line ~1121 onward) currently iterates *all* docs
  and computes BM25 / token-overlap / fuzzy. With postings, the BM25
  candidate set becomes `union(postings[t] for t in query_tokens)`.
  Everything outside that union scores zero on BM25 + token paths
  (only the exact-substring / phrase / heading / filename signals
  could still fire — and those are already cheap because they're
  string-in-string checks, not BM25).

### Honest assessment

* **Build cost**: adds one extra pass per index rebuild. Negligible
  for ≤ 10k docs; the index is cached anyway.
* **Search cost**: for typical 2-3 token queries on a 1000-doc corpus
  with realistic Zipfian token distribution, the union size is
  ~10–100 docs vs the full 1000 — a plausible **5–20× cold-path
  speedup at N≥500**. Below N=100 the win is in the noise.
* **Recall risk**: **non-trivial**. The current loop fires on every
  doc and runs *four* signals (substring, token overlap, BM25, fuzzy)
  + several bonuses (phrase, heading, filename, recency). Restricting
  candidates to the BM25 posting union drops docs that have no
  query-token overlap but might still match on substring / filename /
  phrase. Mitigation: union the BM25 postings with a cheap
  filename-substring shortlist before scoring (filename match is the
  signal users notice most).
* **Code surface**: medium. The forward index already lives in
  `_corpus_index.py`; adding a second dict and a candidate-set helper
  in `_core_search_helpers.py` is mechanical. The scoring loop in
  `core.py:search` would shrink, not bloat.

### Recommendation

Defer to **v2.9** (not v2.8.2 patch). Justification:

1. v2.8.2 already eats the two cheapest wins (touch-throttle,
   strptime cache) and gets us 30 % cold-path improvement on a
   200-doc corpus with **zero recall risk**.
2. Inverted posting lists need a recall-equivalence harness larger
   than the current `test_search_regression_v28.py` — at minimum a
   PersonaMem subset run, since real-world queries have weirder token
   distributions than our synthetic ones.
3. P2 (WAND-style upper-bound pruning) is a strict prerequisite for
   getting full mileage out of posting lists anyway, and pruning on
   top of the existing forward index is a simpler stepping stone.

So the suggested order is:

* **v2.8.2** (now): touch-throttle + strptime cache.
* **v2.8.3** (optional): WAND-style upper-bound pruning on the
  existing forward index. Recall must be byte-identical.
* **v2.9**: inverted postings + candidate-set filter. Ship with
  PersonaMem regression bench.
