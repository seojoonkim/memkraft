# v2.8.2 baseline + v2.8.3 candidate-prefilter analysis

*Run date: 2026-05-14, Mac mini M-series (Asia/Seoul)*

This doc covers:
1. **v2.8.2 baseline** — confirm the touch-throttle + strptime memo
   wins from `perf/v282-touch-throttle` on the standard
   `benchmarks/search_cache_bench.py` workload.
2. **cProfile re-run on v2.8.2** — find the new dominant hot-paths
   now that the v2.8.1 ones are gone.
3. **v2.8.3 candidate prefilter** — recall-preserving optimization
   that skips `_safe_read` + scoring for docs that provably score
   zero (no query-token overlap and no filename match).
4. **v2.8.3 perf numbers** — bench + scaling probe + cProfile delta.
5. **v2.8.4 roadmap** — what the new profile points to next.

## 2. v2.8.2 hot-path profile

`cProfile` over 200 entities × 100 queries (50 matching keywords +
50 no-match `unique-token-*`):

```
tottime  ncalls   function                                    Notes
0.195s   100      core.py:1083 search                         The scoring loop body
0.082s   40000    posix.lstat                                 is_symlink() during glob
0.068s   24132    posix.stat                                  fingerprint mtime checks
0.058s   61134    str.lower
0.051s   800962   str.startswith                              pathlib internals
0.048s   41094    str.split                                   tokenizer
0.042s   42200    pathlib._select_from                        glob internals
0.038s   40300    re.Pattern.findall                          token regex
0.029s   20000    _read_cache.get_or_read
0.025s   20000    core._safe_read
0.023s   20000    pathlib.relative_to                         BM25 path key normalization
0.022s   1094     core._touch_last_accessed   ← v2.8.2 throttle: 3000→1094 ✅
```

Total: **1.173s for 100 queries → 11.73 ms/query** at N=200.

Two big things stand out compared to v2.8.1:

1. **`_touch_last_accessed` collapsed**: 3000 calls / 0.191s on v2.8.1
   → 1094 calls / 0.022s on v2.8.2. That's the touch-throttle win,
   exactly as designed.
2. **`strptime` is gone** from the top-30: memoization eliminated it.
3. **New #1 bottleneck = `all_md_files` + its filesystem-walk
   internals** (lstat + stat + _select_from + parse_parts) ≈ **30 %**
   of total runtime. Directory iteration is now the cap.
4. **`_safe_read` is the #2 single cost** (0.144s cumtime) — and it's
   doing work for *every* doc, including docs that contribute zero
   to the result set.

The #4 observation is exactly what the v2.8.3 prefilter targets.

## 3. v2.8.3 — candidate prefilter (recall-preserving)

### Idea

Before calling `_safe_read` + full scoring on a markdown file, check
whether the doc can possibly contribute to the result set. If not,
skip it.

For `fuzzy=False` (the default), a doc contributes iff:
- some query token appears in the doc's content tokens (drives
  `token_score`, `bm25_score`, and — by the substring-implication
  proof below — `exact_score`), OR
- the query substring is in the filename (drives `exact_score=0.8`),
  OR
- some query token appears in the filename tokens (drives
  `token_score`'s filename leg).

The corpus index already has `doc_token_freqs[md]` cached, so checking
"does any query token appear in this doc?" is an in-memory dict
lookup — no disk read needed.

### Recall safety proof (non-fuzzy mode)

The tokenizer is `\w+` over the lowered text with `len > 1` filter.

Suppose `query_lower in content_lower`. Split the query on whitespace:
each whitespace-fragment of the query is also in content. Any
fragment of length > 1 with at least one word char becomes a search
token in both query and content. So at least one query token is in
the content token set, unless the *entire* query has no
length-≥-2 word-token (e.g. query is `"a"` or `"!!!"`). The prefilter
disables itself when `query_tokens` is empty, so that degenerate case
falls back to the legacy full-scan.

Therefore: for any non-degenerate, non-fuzzy query, every doc that
the legacy loop would have scored > 0 still passes the prefilter.
**Zero recall risk.**

### Cache-staleness safety

The corpus index uses `_compute_fingerprint(files)` over
`(path, mtime_ns, size)`. The v2.8.1 fast path
(`trust_write_hooks=True`) skips the per-file stat scan when no
writes have happened through MemKraft's write API since the last
build.

A failure mode: a caller bypasses MemKraft and writes the file
directly (e.g. `entity_file.write_text(...)`). The cache stays
"fresh" by generation but the content is stale. Legacy search masked
this by reading the file again in the scoring loop. The prefilter
would otherwise refuse to read and miss the new content.

**Mitigation** (v2.8.3): the index now stores `doc_stat[md] =
(mtime_ns, size)`. When the prefilter is about to skip a doc, it
does **one extra `md.stat()` call** to compare against the cached
tuple. If they match → safe to skip. If not → fall through to
scoring. One stat per skipped doc is still much cheaper than reading
and tokenizing the whole file.

Regression test `test_modification_invalidation` (which exercises
exactly this raw-write bypass) confirms this works: 1300/1303 tests
pass, no regressions.

### Implementation summary

* `src/memkraft/_corpus_index.py`
  * `CorpusIndex.doc_stat: Dict[Path, tuple]` — `(mtime_ns, size)`
    captured at build time.
  * `_build_index` populates it from the existing fingerprint pass
    (free — we already had the stats).
* `src/memkraft/core.py:search`
  * After loading the index, build `_query_token_set` once.
  * Inside the per-doc loop, before `_safe_read`, run:
    * intersect `_query_token_set` with `doc_token_freqs[md]` (O(|q|))
    * if empty, check `query_lower in filename_lower`
    * if empty, intersect with filename tokens
    * if everything is empty, do **one** `md.stat()` to confirm the
      cache is fresh → `continue`
* Env knob: `MEMKRAFT_DISABLE_CANDIDATE_PREFILTER=1` bypasses the
  prefilter entirely (regression-test escape hatch, parallels
  `MEMKRAFT_DISABLE_TOUCH_LAST_ACCESSED`).

## 4. v2.8.4 roadmap — what the new profile points to

After v2.8.3 the biggest remaining costs (200-doc, 100-query profile):

```
tottime  ncalls   function                                       Notes
0.147s   100      core.search                                    loop body
0.082s   40000    posix.lstat (via is_symlink in all_md_files)   directory walk
0.068s   34000    posix.stat                                      fingerprint + prefilter stat
0.062s   ...      _select_from / glob internals
0.058s   ...      str.lower
```

### Candidate A — file-list caching (v2.8.4 most likely)

`all_md_files` is called twice per `search()` call (once via
`get_corpus_index`, once for the scoring loop) and yields ~200 files.
With the corpus index trusted (`trust_write_hooks=True`), the
markdown file set is *known* — `doc_token_freqs.keys()` is exactly
the file list (modulo race-deleted docs). Replacing the second call
with `list(_idx.doc_token_freqs.keys())` would eliminate ~50 % of the
remaining `lstat`/`is_symlink` cost.

Estimated win: another 10–15 % cold-path improvement.

Risk: low. The fast-path already checks `path_set_hash` against the
caller's current path set. Edge: files added between the index build
and the search call would be missed by the loop — same edge case
that already exists in v2.8.2 for `_safe_read` race-deletes; would
need a "fallback to fresh walk" handler.

### Candidate B — drop `relative_to` from the hot loop

`md.relative_to(self.base_dir)` is called 20000 / 14530 times
(0.098s cumtime). It's just to build the result dict's `"file"`
field. Replacing with `str(md).replace(str(self.base_dir) + "/", "", 1)`
would shave ~50 % off, but the function is already cheap per call;
the absolute win is small (~2 %).

### Candidate C — fold `is_symlink` into a single `lstat`

`all_md_files` does `glob("*.md")` (which already stat's via
`_select_from`) then `is_symlink()` (which `lstat`s again). On macOS
this double-stat is unavoidable through pathlib, but rolling our own
walk via `os.scandir` (which returns `DirEntry.is_symlink()`
inline — no extra stat) would eliminate the second lstat pass.
That's the 0.082s `lstat` cost basically halving.

Estimated win: 8–12 % cold-path on N≥500 corpora.

Risk: low; `os.scandir` is stdlib, the only edge is symlink
semantics (already handled by `DirEntry.is_symlink()`).

### Candidate D — defer P2 WAND pruning

The v2.8.2 analysis recommended WAND-style upper-bound pruning as
v2.8.3. With the candidate prefilter shipped, WAND's marginal value
drops sharply: the prefilter already short-circuits the largest
class of "doc contributes zero" cases. WAND would only help when
*some* query tokens hit the doc but the resulting BM25 upper bound
is still below the top-K threshold — a narrower win, and one with
real recall risk on the composite scoring formula.

**Recommend**: keep WAND on the v2.9 roadmap (paired with inverted
postings), not v2.8.4. Pick file-list caching (A) + scandir (C)
first — they're zero-recall-risk and target the next-biggest cost.

### v2.8.4 suggested order

1. File-list caching (A). +10-15 % cold-path. ~50 LoC change.
2. `os.scandir`-based `all_md_files` (C). +8-12 %. ~30 LoC change.
3. (Optional) `relative_to` → string-strip (B). +1-2 %.

Combined v2.8.4 estimate: **another 15-25 %** on top of v2.8.3 for
N≥500 corpora.

## 5. Honest cost accounting

The v2.8.3 prefilter is **not free for everyone**:

* On corpora < 50 docs with dense queries (most query tokens appear
  in most docs), the per-doc dict intersection costs a few µs per
  doc and saves nothing. The bench shows this as ~3 % regression on
  some warm-cache micros — within noise but real.
* The optional stat-check for stale cache adds one `os.stat()` per
  skipped doc. On networked filesystems (NFS) that could be slower
  than reading from a local cache. Workaround: set
  `MEMKRAFT_DISABLE_CANDIDATE_PREFILTER=1`.
* Cache memory: `doc_stat` adds ~24 bytes per doc to the index. At
  10k docs that's 240 KB — negligible.
