# MemKraft v2.8.0 — Performance Analysis & Improvement Roadmap

**Date:** 2026-05-13
**Author:** zeon (sub-agent benchmark run)
**Branch:** `perf/v281-search-hot-path`
**Status:** Fix 1 + Fix 2 implemented & tested (1300/1300 passing). PR-ready.

---

## TL;DR

- **Search latency is O(N) in corpus size today.** At 1000 entities a single `mk.search()` costs ~176ms.
- **Root cause:** every search re-tokenizes every document via `re.findall`, even though tokens are already pre-computed in the cached corpus index (`_corpus_index.doc_token_freqs`).
- **Secondary cause:** `best_token_snippet` re-tokenizes every line of every matched document to pick the snippet window.
- **Fix shipped on `perf/v281-search-hot-path`:** two surgical edits, no API change.
  - `search()` reuses `doc_token_freqs[md].keys()` instead of calling `_search_tokens(content_lower)`
  - `best_token_snippet()` uses substring containment instead of per-line tokenization
- **Result:** **1.3–2.3× faster** end-to-end across all bench workloads; **all 1300 unit tests still pass**.

## 4. The two fixes (already applied on `perf/v281-search-hot-path`)

### Fix 1 — Reuse pre-tokenized TF map (`core.py:1151`)

```python
# Before
content_tokens = set(self._search_tokens(content_lower))   # O(doc_len)
...
tf_map = doc_token_freqs.get(md, {})

# After
_tf_map_hot = doc_token_freqs.get(md)
if _tf_map_hot is not None:
    content_tokens = _tf_map_hot.keys()
else:
    content_tokens = set(self._search_tokens(content_lower))   # fallback for races
...
tf_map = _tf_map_hot if _tf_map_hot is not None else doc_token_freqs.get(md, {})
```

The corpus index already builds `doc_token_freqs[md]: Dict[str, int]` — its
`.keys()` view *is* the set of document tokens. The previous code threw that
away and re-tokenized the entire document body on every search.

### Fix 2 — Substring containment in `best_token_snippet` (`_core_search_helpers.py:114`)

```python
# Before
for idx, line in enumerate(lines):
    line_tokens = set(search_tokens_fn(line))           # 40+ findalls per matched doc
    hits = len(query_set & line_tokens)

# After
for idx, line in enumerate(lines):
    if not line:
        continue
    hits = sum(1 for t in query_set if t in line)        # plain substring
    if hits > best_hits:
        best_hits = hits
        best_idx = idx
        if best_hits == len(query_set):
            break                                        # can't beat full match
```

Substring check over-counts only when a query token is a strict prefix/infix of
a longer word (e.g. `"ai"` inside `"email"`). Because this routine only picks
*which* snippet window to display — not relevance — the slight over-count is
harmless. Relevance scoring still goes through the precise BM25/IDF path with
the cached TF map.

## 5. Top 5 improvement opportunities (next steps)

Ranked by `impact × tractability` after the two fixes above.

### P1 — Lazy/incremental fingerprint for `_corpus_index`
**Impact:** ~20–30% extra at 500+ docs · **Effort:** medium
- `_compute_fingerprint` stat-walks every file on every search (185 ms at 500 docs).
- When nothing has changed (the common case), this still costs N `os.stat()` calls.
- Options:
  (a) Track a directory mtime watermark and short-circuit when unchanged.
  (b) Cache the previous file list + stat snapshot; re-stat only when wall-clock
      since last build > some threshold (e.g. 1s) or after a known write.
  (c) Wire `mk.update()` / `mk.track()` to invalidate the cache directly,
      removing the need to stat at all on the read path.
- (c) is the cleanest and fastest — write path is well-defined inside MemKraft
  and already small, so adding an `_corpus_index.invalidate()` call is local.

### P2 — Skip body re-read for low-score documents
**Impact:** ~15–25% at 500+ docs · **Effort:** small
- `_safe_read` cumulative time is 0.5 s in the 500-doc profile, called for
  *every* doc regardless of whether the query has any chance of matching.
- We have `tf_map` and `filename_tokens` cached in the index — we can compute
  a cheap *upper bound* on `token_score + bm25_score` from those alone, without
  reading the body. If the upper bound is below a top-k threshold, skip the body
  read entirely.
- Equivalent of WAND / block-max-WAND pruning in classic IR.

### P3 — Inverted posting list in `_corpus_index`
**Impact:** Closer to O(unique tokens × matching docs) instead of O(N) · **Effort:** medium
- Add `token_to_docs: Dict[str, List[Path]]` to `CorpusIndex`.
- `search()` then iterates only docs that contain at least one query token,
  instead of all N docs.
- For typical queries (2–4 tokens, low DF), this turns the per-query cost from
  ~N×constant into ~match-count×constant.
- Combined with P2 this is the right path to make search **sub-linear**.

### P4 — Pre-compute `doc_token_freqs` keys as `frozenset`
**Impact:** ~5–8% · **Effort:** trivial
- Today Fix 1 uses `_tf_map_hot.keys()` — fine, but Python recomputes hash
  membership against the dict on every `in` check.
- Storing a `frozenset` alongside `tf_map` (e.g. `doc_token_sets: Dict[Path, frozenset]`)
  avoids the dict-key hashing overhead and makes `query_set & token_set`
  intersections vectorized in CPython.

### P5 — PersonaMem `novel_suggestion` floor (33%) — diagnosis, not optimisation
**Impact:** semantic accuracy, not latency · **Effort:** medium
- Historical n=20 runs show `novel_suggestion` capped at 33% across baseline /
  hybrid / memkraft variants — i.e. the corpus index can't help when the
  question requires reasoning beyond stored facts.
- Worth investigating whether MemKraft's `recall` (multi-hop) path is being
  invoked here; if not, this is the question type where MemKraft *should* shine
  and we're under-using it.
- LME oracle is already at 98% semantic-majority — diminishing returns there.
  PersonaMem is the bench to push on.
